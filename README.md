## M1 — `set16`, порядок байтів

`get16` склеює (`lo | (hi << 8)`), `set16` розрізає: `lo = value & 0xFF`, `hi = value >> 8`; молодший лягає за **меншою** адресою.
Перевірка `addr + 1 >= MEM_SIZE` стоїть **до** запису: інакше невдалий виклик лишив би напівзапис (молодший байт уже в пам'яті, старший — ні).

Дамп порядку байтів (`checks/lab-03.txt`):

```
> set16 0 0x1234
> dump 0 4
0000: 34 12 00 00                                      |4...|
> get16 0
get16(0x0) = 0x1234
> get 0
mem[0x0] = 52
> get 1
mem[0x1] = 18
> # крайні випадки: останній байт коробки, за межею
> set16 0xFFE 0xBEEF
> dump 0xFF0 16
0FF0: 00 00 00 00 00 00 00 00 00 00 00 00 00 00 EF BE  |................|
> set16 0xFFF 0xBEEF
помилка: адреса поза пам'яттю (потрібні addr і addr+1)
> get16 0xFFF
помилка: адреса поза пам'яттю (потрібні addr і addr+1)
> set16 0 0x10000
помилка: значення не вміщується в 16 біт
```

`set16 0 0x1234` → за адресою 0 байт `34`, за адресою 1 байт `12`. Це little-endian, і саме так
лежать 16-бітні операнди в потоці інструкцій (`LOADH H, 0x0800` = `28 00 08`).
Остання пара, яка ще влазить, — `0xFFE`/`0xFFF`; `set16 0xFFF …` відхиляється.

## M2 — що реалізовано (розміри з ISA.uk.md)

| Опкод | Мнемоніка | Розмір | | Опкод | Мнемоніка | Розмір |
| --- | --- | --- | --- | --- | --- | --- |
| `00` | `HALT` | 1 | | `26` | `MOV A, B` | 1 |
| `01` | `NOP` | 1 | | `27` | `MOV B, A` | 1 |
| `02` | `OUT` (A як символ) | 1 | | `28` | `LOADH H, imm16` | 3 |
| `03` | `OUTN` (A як число + пробіл) | 1 | | `29` | `LOAD A, [H]` | 1 |
| `20`/`21` | `LOADI A/B, imm8` | 2 | | `2A` | `STORE [H], A` | 1 |
| `22`/`23` | `LOAD A/B, [addr16]` | 3 | | `2B` | `INCH` | 1 |
| `24`/`25` | `STORE [addr16], A/B` | 3 | | `2C` | `DECH` | 1 |
| | | | | `2D` | `HLOW` (opt) | 1 |

Рішення, які я прийняв і які тут записую:
- `PC` рухається **рівно на розмір інструкції**; `HALT` теж зсуває `PC` (стоїть після нього).
- Перед виконанням перевіряю, що **вся** інструкція вміщується в пам'ять (`pc + size <= MEM_SIZE`), бо безпосередній операнд теж лежить у пам'яті.
- Помилка (`LOAD` поза пам'яттю, невідомий опкод…) → `step` повертає `false`, `PC` **лишається на інструкції, що відмовила**; пам'ять і регістри не міняються.
- Адреса `>= MEM_SIZE` **відхиляється, а не загортається**. Єдине, що загортається, — сам 16-бітний `H` при `INCH`/`DECH` (арифметика `uint16_t`); при наступному `LOAD A,[H]` адреса перевіряється заново.
- `LOAD`/`LOADI` прапорців **не чіпають** (ISA §3).
- `run` має ліміт кроків (100000), щоб помилка в програмі не підвісила REPL.
- Група `0x1_` (ALU), стрибки тощо — з ваших Lab 2/4; сюди ця лаба їх не додає.

## M3 — програма, що користується даними

Дані на `0x800` (`41 42 43 00` = `ABC`), код на `0x000`. Один регіон — код, інший — дані, а коробка спільна.

### a) за абсолютною адресою

```
0000  22 00 08   LOAD A, [0x0800]
0003  02         OUT
0004  00         HALT
```

```
> load 0x800 41 42 43 00
> load 0 22 00 08 02 00
> dump 0 8
0000: 22 00 08 02 00 00 00 00                          |".......|
> dump 0x800 4
0800: 41 42 43 00                                      |ABC.|
> trace on
> run
0000  22 00 08  LOAD A, [0x0800]      ; A=41 B=00 H=0000 PC=0003
0003  02        OUT                   ; A=41 B=00 H=0000 PC=0004
0004  00        HALT                  ; A=41 B=00 H=0000 PC=0005
термінал: A
виконано інструкцій: 3 (HALT)
> trace off
> regs
A=41 B=00 H=0000 PC=0005 SP=0FFF  Z=0 N=0 C=0  [HALT]
>
```

### b) через `H` (сім інструкцій)

```
> load 0 28 00 08 29 02 2B 29 02 00
> trace on
> run
0000  28 00 08  LOADH H, 0x0800       ; A=00 B=00 H=0800 PC=0003
0003  29        LOAD A, [H]           ; A=41 B=00 H=0800 PC=0004
0004  02        OUT                   ; A=41 B=00 H=0800 PC=0005
0005  2B        INCH                  ; A=41 B=00 H=0801 PC=0006
0006  29        LOAD A, [H]           ; A=42 B=00 H=0801 PC=0007
0007  02        OUT                   ; A=42 B=00 H=0801 PC=0008
0008  00        HALT                  ; A=42 B=00 H=0801 PC=0009
термінал: AB
виконано інструкцій: 7 (HALT)
> trace off
> regs
A=42 B=00 H=0801 PC=0009 SP=0FFF  Z=0 N=0 C=0  [HALT]
>
```

`H` прокрутився `0x0800 → 0x0801`, а `A` — `41 → 42`: це `p = &data[0x800]; a = *p; ++p; a = *p;`.
Виводу `AB` саме й очікували.

## M4 — вказівник хоста проти адреси гостя

`CPU` тримає **один** вказівник хоста, `Memory* mem` («де лежить вся коробка»), а все, що
для програми-гостя є «місцем», — `uint16_t pc`, `uint16_t h`, `uint16_t sp` — це **числа-індекси** від 0 до 4095,
а не `Byte*` усередину `data`. Причина в тому, що адреса гостя й адреса хоста — різні речі. `0x0800` означає
«комірка №2048 цієї коробки» на будь-якій машині й у будь-якому запуску, і його можна покласти в регістр, записати
в пам'ять двома байтами, вивести в дамп, порахувати. Вказівник хоста — це адреса в **моєму процесі**: щоразу інша
(ASLR), безглузда для гостя й недійсна після перевиділення пам'яті. Дивіться самі: `hostdump` двічі, перші 8 байтів
`CPU` — це `Memory*`, а `FF 0F` на зсуві 14 — `sp = 0x0FFF` гостя, що не змінюється:

```
запуск 1: 0000: E0 04 A0 60 F5 7F 00 00 00 00 00 00 00 00 FF 0F  |...`............|
запуск 2: 0000: E0 04 60 1D C7 7F 00 00 00 00 00 00 00 00 FF 0F  |..`.............|
```

Баг, до якого призводить змішування: взяти `&mem.data[0x800]` (адресу хоста) і покласти її в `H` чи в пам'ять гостя, чекаючи, що
`LOAD A,[H]` піде туди. Не вийде з двох причин: вказівник хоста — 64 біти, а `H` — 16, тож старші 48 біт мовчки відрізаються і
лишається випадкове число; і навіть ціле воно інше при кожному запуску. Зворотний баг — індексувати `mem.data[guest_addr]`
**без перевірки меж**: тоді гість отримує читання й запис у пам'ять хоста (саме це ASan і ловить нижче).
`H` — це вказівник, який видно в дампі, бо він живе всередині машини.

### Навмисний вихід за межу + звіт ASan

`ember/asan_demo.cpp`: `Memory mem{}; mem.data[MEM_SIZE] = 1;` — комірка №4096 уже чужа. Фрагмент звіту (повний — `traces/asan-report.txt`):

```
ember/asan_demo.cpp:6:15: runtime error: index 4096 out of bounds for type 'unsigned char [4096]'
==167==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7f20ccc01020 at pc 0x55c6d476c57d bp 0x7ffd772aca80 sp 0x7ffd772aca70
WRITE of size 1 at 0x7f20ccc01020 thread T0
    #0 0x55c6d476c57c in main ember/asan_demo.cpp:6
Address 0x7f20ccc01020 is located in stack of thread T0 at offset 4128 in frame
    #0 0x55c6d476c318 in main ember/asan_demo.cpp:3
    [32, 4128) 'mem' (line 4) <== Memory access at offset 4128 overflows this variable
SUMMARY: AddressSanitizer: stack-buffer-overflow ember/asan_demo.cpp:6 in main
```

Три рядки, які тут важать: **тип** (`stack-buffer-overflow`), **що й де** (`WRITE of size 1`, `asan_demo.cpp:6`) і **який об'єкт**
(`[32, 4128) 'mem' <== Memory access at offset 4128 overflows`: об'єкт `mem` займає зсуви від 32 до 4128 у кадрі, а звернення було за зсувом 4128,
тобто на перший байт одразу після кінця — рівно «один за край»). UBSan перед ASan каже те саме з іншого боку: `index 4096 out of bounds for type 'unsigned char [4096]'`.

**Виправлення:** перевірка меж повернена на місце: `mem_set` повертає `false` для `addr >= MEM_SIZE`, `step` відмовляє з повідомленням, а не записує.
Це і є «вказівник із перевіркою меж» у VM. Перевірка в `checks/lab-03.txt`: `LOAD A,[0x1000]` → `стоп: LOAD: адреса 0x1000 поза пам'яттю`, `PC` лишається на місці.

## Advanced

**`void dump(const void* ptr, std::size_t n)`** (`ember/hexdump.cpp`) — дамп будь-якого об'єкта хоста; `void*` нічого не знає про розмір
і тому всередині одразу стає `const unsigned char*`. Команда `hostdump` робить `dump(&cpu, sizeof(cpu))` (див. M4).

**Копіювання 4 байтів лише через `H` і `MOV`** (`traces/copy4.in` → `traces/copy4.txt`, 43 інструкції, 45 байтів коду).
Для кожного байта: `LOAD A,[H]`, `MOV B,A` (паркую байт у `B`), `INCH`×4 (H стрибає на «поверх» призначення),
`MOV A,B`, `STORE [H],A`, `DECH`×3 (назад до наступного джерела). Джерело `0x800..0x803`, призначення `0x804..0x807`, тож різниця
адрес — 4 і `INCH` рахує її руками. Чесне зауваження: `A` пережив би `INCH`, і `MOV` тут потрібен не для коректності, а щоб показати, що `A`/`B`
тримають значення, а `H` — місце. Кінець трасування:

```
> trace off
> regs
A=EF B=EF H=0807 PC=002D SP=0FFF  Z=0 N=0 C=0  [HALT]
> dump 0x800 8
0800: DE AD BE EF DE AD BE EF                          |........|
```

`DE AD BE EF` лежить по обидва боки.

## Відповіді на питання захисту (для підготовки — на захисті відповідайте своїми словами)

1. `int x = 65; int* p = &x;`: коробка `x` зі `65` і стрілка від коробки `p`. `p` — **адреса** `x`; `*p` — те, що за адресою (`65`); `&p` — адреса самої `p` (тип `int**`).
2. `p + 1` додає `sizeof(*p)` байтів, тож залежить від типу: `int*` стрибає на 4, `char*` на 1.
3. У `void*` немає розміру того, на що він вказує, — компілятор не знає, скільки байтів читати й на скільки зсуватись.
4. Читання `float` через `int*` порушує правила аліасингу (UB). Чесно: `memcpy` у `uint32_t` або дамп байтів.
5. Вказівник хоста — адреса в моєму процесі (щоразу інша); адреса гостя — число-індекс у коробці. Змішування: див. M4.
6. `inc(int* p)`; `inc(int x)` працює з копією у власному кадрі, яка вмирає при поверненні.
7. Один байт називає лише `0x00..0xFF` (256 адрес), а пам'яті 4096 (12 біт); `H` — 16 біт.
8. `LOAD A, [H]` ↔ `Byte a = *p;` (розіменування). `INCH` ↔ `++p;` (рух на один елемент, а тут елемент — байт).
